# Решения по сайту (ADR-стиль)

## D1. Хранение заявок — SQLite
**Решение:** SQLite (файл на постоянном диске) + SQLAlchemy 2.0.
**Почему:** объём — единицы заявок в день; одна зависимость, ноль инфраструктуры, файл легко бэкапить.
Курсорная выдача боту по `id` работает без внешней БД.
**Альтернативы:** JSONL-файл (плохо фильтруется и портится при конкурентной записи),
Postgres (избыточен и требует бесплатного хостинга с БД), внешний сервис (лишняя зависимость).
**Когда пересмотреть:** >100 заявок в день, несколько инстансов API, потребность в аналитике воронки.

## D2. Разделение фронта и бэкенда
**Решение:** Next.js на Vercel, FastAPI на отдельном хостинге с постоянным диском.
**Почему:** в брифе Next.js назван предпочтительным; SQLite требует постоянного диска, которого у Vercel нет.
**Риск:** два деплоя и CORS — снимается строгим списком источников и env-переменной.

## D3. Дедупликация на сервере
**Решение:** серверное окно 10 минут по нормализованному номеру + `client_request_id`.
**Почему:** бриф прямо требует, чтобы повтор (в т.ч. двойной клик) не создавал вторую заявку;
браузерным проверкам доверять нельзя. `client_request_id` дополнительно делает сабмит идемпотентным при ретрае.

## D4. Источник заявки
**Решение:** `source` собирается на клиенте (`page_url`, `referrer`, `utm_*`, `form_id`, `cta_variant`)
и сохраняется как есть; никакой сторонней аналитики.
**Почему:** бриф требует знать, из какого объявления/страницы пришёл клиент, но не требует сбора лишних данных.

## D5. Валидация номера на обеих сторонах
**Решение:** один и тот же алгоритм нормализации в `web/lib/validation/phone.ts` и `api/app/utils/phone.py`.
**Почему:** мгновенная подсказка в интерфейсе + гарантия на сервере; риск расхождения закрывается общим набором тест-кейсов.

## D6. Только белорусские номера
Прочие форматы отклоняются с понятной подсказкой — это требование брифа, а не самодеятельность.
